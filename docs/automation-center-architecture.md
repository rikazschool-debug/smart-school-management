# مركز الأتمتة الذكية في ركاز — المرحلة الأولى: الحصر والتحليل والتخطيط المعماري

> الحالة: **خطة بانتظار اعتماد مدير النظام**. لم يُعدَّل أي كود تشغيلي أو قاعدة بيانات، ولم تُنشأ أو تُشغَّل أي جدولة أو قاعدة أتمتة أو إشعار، ولم يُمَس الإنتاج، ولم يُنشر شيء. Webhooks تبقى يدوية.
>
> المصدر: الكود في هذا المستودع + قراءة فقط من قاعدة الاختبار (cron.job، cron.job_run_details، pg_proc، pg_trigger، information_schema) بتاريخ 2026-11-26.

---

## 0. الخلاصة التنفيذية

- ركاز يملك اليوم **13 مهمة مجدولة** في `pg_cron` و**نحو 35 دالة إشعار/تنبيه** متفرقة لكل قسم، وجميعها تكتب في جدول واحد `notifications` عبر `_notify` مع منع تكرار بمفتاح `(user_id, dedupe_key)`.
- لا يوجد محرك قواعد عام. الأتمتة الحالية **مُبرمجة داخل كل قسم** (hard-coded) وتعمل بشكل سليم؛ يجب **عدم استبدالها أو تكرارها**.
- يوجد بالفعل نمطان صالحان لإعادة الاستخدام: **Outbox** (`acct_outbox`, `evt_outbox`, `sf_outbox`, `api_deliveries`) و**Triggers تُدرج في قائمة انتظار** (`_api_emit_trg` على 6 جداول).
- البنية المقترحة: **محرك داخل Postgres بالكامل** (SQL + SECURITY DEFINER) بدون خدمات خارجية: Outbox للأحداث ← طابور تنفيذ بـ `FOR UPDATE SKIP LOCKED` ← إجراءات داخلية مسجلة في دليل مغلق (Action Registry) تستدعي RPCs القائمة فقط.
- **لا مهمة cron جديدة في الشريحة الأولى**: يُضاف استدعاء `automation_tick()` إلى مهمة قائمة (`rikaz-homework-tick` كل 15 دقيقة) بشرط خروج فوري عند فراغ الطابور.
- **أول شريحة رأسية مقترحة**: «متابعة التكليفات الإدارية المتأخرة» → إشعار داخلي لمُسنِد التكليف فقط (لا مال، لا واتساب، لا تعديل بيانات)، بقاعدة معطلة افتراضيًا، ومحاكاة قبل الاعتماد، واعتماد مدير النظام.

## 2. تحليل فرص الأتمتة لكل قسم

**القاعدة:** الإجراء التلقائي = إشعار داخلي، أو مهمة متابعة، أو اقتراح/مسودة. أي إجراء يغيّر مالًا أو اعتمادًا أو صلاحية أو بيانات طالب **لا يُنفَّذ تلقائيًا** ويتحول إلى «طلب يحتاج قرارًا بشريًا».

| القسم | أحداث محفزة (مصدرها) | شروط ممكنة | إجراءات تلقائية مسموحة | تحتاج موافقة بشرية | ممنوعة تلقائيًا | قائم يُعاد استخدامه / لا يُكرر |
|---|---|---|---|---|---|---|
| الإدارة المدرسية (تكليفات/طلبات/نماذج) | `adm_events` created/done/returned/blocked؛ تجاوز `due_date` | المدرسة، القسم، الأولوية، عدد أيام التأخير | إشعار للمُسنِد/مدير المدرسة؛ إنشاء مهمة متابعة | إعادة إسناد التكليف | إغلاق التكليف أو تغيير حالته | `adm_daily_reminders` (تذكير قبل يوم للمكلَّف) — لا يُكرر |
| المناوبات | `adm_events` duty published/cancelled | الموقع، اليوم | إشعار احتياط | تبديل المناوب | تعديل الجدول المنشور | تذكير المناوبة في `adm_daily_reminders` |
| الاجتماعات والقرارات | meeting created/minutes_confirmed/decision_added | نوع القرار | مهمة متابعة لتنفيذ القرار | — | تعديل المحضر | `_adm_*` |

**فرص تقليل العمل اليدوي ذات الأثر الأعلى (لا تكرر الموجود):**
1. متابعة التكليفات المتأخرة للمُسنِد (لا يوجد حاليًا — التذكير الحالي للمكلَّف قبل يوم فقط).
2. مهام متابعة تلقائية لقرارات الاجتماعات.
3. تصعيد طلبات `api_inbox` المعلقة أكثر من X ساعة لمدير النظام.
4. تذكير اعتماد المرحلة التالية في المشتريات بعد مهلة (يُراجع مقابل `pc_alerts_tick` قبل البناء).
5. ملخص يومي واحد لكل مدير مدرسة بدل إشعارات متفرقة (قيمة عالية، يأتي لاحقًا).

## 3. التصميم المعماري للمحرك

### 3.1 القرار التقني

**محرك داخل Postgres** (SQL + plpgsql + SECURITY DEFINER) مع واجهة TanStack تقرأ/تكتب عبر RPCs مالك/مفوَّض فقط.
السبب: كل الإجراءات الداخلية المسموحة أصلًا دوال SQL (`_notify`, `adm_*`)، الصلاحيات في RLS، والخادم يعمل على Cloudflare Workers (بلا عمليات طويلة ولا طوابير مدمجة). لا Redis، لا خدمة طوابير خارجية، لا pg_net للأتمتة الداخلية، لا ذكاء اصطناعي في التنفيذ.

```text
 RPC قائمة (adm_*, mt_*, sf_* ...)
        │ تكتب كالعادة
        ▼
 سجل أحداث القسم (adm_events, mt_events ...)
        │ AFTER INSERT trigger خفيف: يخرج فورًا إن لم توجد قاعدة نشطة لهذا الحدث
        ▼
 au_outbox  (نفس المعاملة → لا فقد للأحداث)
        │ automation_tick() — FOR UPDATE SKIP LOCKED, دفعات
        ▼
 مطابقة القواعد (au_rule_versions المعتمدة) → تقييم الشروط (JSON محدود)
        ▼
 au_jobs (طابور تنفيذ: فوري/مؤجل run_at، أولوية، idempotency_key)
        ▼
 Action Registry (قائمة مغلقة) → RPC داخلية قائمة (_notify, adm_task_create ...)
        ▼
 au_runs / au_run_steps (سجل تنفيذ) — فشل نهائي → dead (DLQ)
```

### 3.2 الجداول المقترحة (إضافية فقط، بادئة `au_`)

| الجدول | الغرض |
|---|---|
| `au_event_types` | دليل الأحداث (code، القسم، الجدول المصدر، المتغيرات المتاحة وأنواعها، حساسية كل متغير، `psec` لربط `section_enabled`) |
| `au_action_types` | دليل الإجراءات المغلق (code، الدالة المنفذة، مستوى الخطر، `requires_approval`، الحد الأقصى لكل تشغيل) |
| `au_rules` | القاعدة (org، النطاق: مدارس محددة/جميع المدارس صراحة، الحالة draft/active/paused/archived، `current_version`) |
| `au_rule_versions` | نسخ غير قابلة للتعديل بعد الاعتماد: trigger، conditions (شجرة AND/OR محدودة العمق ≤ 4)، actions (≤ 10، تسلسلي/متوازي)، delay، approved_by/at، fingerprint |
| `au_outbox` | الأحداث الواردة (event_type، org، school، entity_id، payload مختصر، `dedupe_key` فريد، depth) |
| `au_jobs` | طابور التنفيذ (status: pending/running/done/failed/dead/cancelled، run_at، attempts، next_at، lock، `idem_key` فريد) |
| `au_runs`, `au_run_steps` | سجل كل تشغيل وخطوة (مدة، نتيجة، خطأ مختصر، simulated) |
| `au_settings` | لكل منظمة: `kill_switch`، حدود، نافذة هادئة |
| `au_log` | تدقيق التغييرات (إنشاء، تعديل مسودة، اعتماد، تفعيل، إيقاف، إيقاف طارئ، إعادة محاولة) |

كل جدول: GRANT صريح ← RLS ← سياسات قراءة عبر `au_can(_org,_action)`؛ **لا كتابة مباشرة** للمستخدمين — RPCs فقط (نفس نمط api_* وpc_*).

### 3.3 خصائص المحرك

| المطلب | الحل |
|---|---|
| Event Bus | triggers على سجلات الأحداث القائمة (لا تعديل في RPCs الأقسام)؛ الفحص الأول `exists(select 1 from au_rules where active and event=…)` بفهرس جزئي، مثل `_api_emit` |
| Transactional Outbox | الإدراج في `au_outbox` داخل نفس معاملة الحدث؛ إذا تراجعت المعاملة لا يوجد حدث |
| Job Queue | `au_jobs` + `FOR UPDATE SKIP LOCKED` + دفعات (افتراضي 200) + حد زمني للتشغيل (≤ 3 ثوانٍ ثم يتوقف ويكمل في الدورة التالية) |
| الشروط المتفرعة | مُقيِّم plpgsql لشجرة JSON بمشغلات محدودة (=, ≠, >, <, in, between, is_empty, contains) على متغيرات من الدليل فقط — لا SQL ديناميكي من المستخدم إطلاقًا |
| التنفيذ الفوري/المؤجل | `run_at = now()` أو `now() + delay`؛ «فوري» = الدورة التالية |
| تسلسلي/متوازي | الخطوات مرتبة داخل الوظيفة؛ «متوازي» = وظائف مستقلة بنفس run |
| Idempotency | `au_outbox.dedupe_key` فريد + `au_jobs.idem_key = rule_version:entity:action:period` فريد + `_notify` يمنع التكرار بـ `dedupe_key` |
| التزامن | `SKIP LOCKED` + `pg_try_advisory_xact_lock(hash(org))` لمنع تشغيلين متداخلين للمنظمة نفسها |
| إعادة المحاولة | تأخير أُسّي 1، 5، 30 دقيقة، أقصى 3 محاولات |
| DLQ | `status='dead'` بعد آخر محاولة + إشعار مدير النظام مرة واحدة يوميًا |
| التعارضات والأولويات | `priority` على القاعدة؛ قاعدة واحدة لكل (حدث، كيان، إجراء، مستلم) خلال نافذة `cooldown` |
| منع الحلقات | أحداث يولدها المحرك تحمل `origin='automation'` و`depth`؛ الحد الأقصى depth = 2، ولا تُطابَق القواعد على أحداث المحرك في المرحلة الأولى أصلًا |
| الإصدارات | `au_rule_versions` غير قابلة للتعديل بعد الاعتماد؛ التعديل = مسودة جديدة؛ التنفيذ يقرأ النسخة المعتمدة المثبتة في الوظيفة |
| الإيقاف الطارئ | `au_settings.kill_switch` لكل منظمة + مفتاح منصة؛ يفحصه `automation_tick` وكل وظيفة قبل التنفيذ |
| تفعيل الأقسام | كل حدث/إجراء مرتبط بـ `psec`؛ `section_enabled=false` يوقف مطابقته |
| التدقيق والمراقبة | `au_log` + `au_runs` (مدة، عدد، أخطاء) + مؤشرات في لوحة القيادة |

### 3.4 الجدولة دون تكلفة إضافية

- **الشريحة الأولى:** لا `cron.schedule` جديد. يُلحَق `select public.automation_tick();` بأمر `rikaz-homework-tick` القائم (كل 15 دقيقة = 96 تشغيل/يوم موجودة أصلًا). الدالة تخرج خلال < 5 ms عند فراغ الطابور وعدم وجود قواعد زمنية مستحقة.
- الأحداث الزمنية (مثل «تأخر التكليف») تُولَّد بمسح مفهرس محدود (`due_date < school_today()` + حالات مفتوحة) **فقط للمنظمات التي لديها قاعدة نشطة من هذا النوع**، مرة يوميًا لكل قاعدة.
- إن احتاج المستخدم زمن استجابة أقل من 15 دقيقة لاحقًا: مهمة مستقلة كل 5 دقائق = 288 تشغيل/يوم — قرار للمستخدم.

## 5. الصلاحيات والأدوار

قسم جديد في دليل الصلاحيات `automation` بأفعال مستقلة:
`view`, `create`, `edit_draft`, `simulate`, `approve`, `toggle`, `templates`, `view_runs`, `retry`, `kill_switch`.

- تحديث `docs/permissions-matrix.md` عند البناء.

## 9. أول شريحة رأسية مقترحة (تنتظر الاعتماد)

**«متابعة التكليفات الإدارية المتأخرة»**

- **الحدث:** `adm.task.overdue` — تكليف `adm_tasks` حالته new/in_progress/returned/blocked وتجاوز `due_date` حسب `school_today()`.
- **الشروط المتاحة:** المدرسة، القسم، الأولوية، عدد أيام التأخير (≥ N).
- **الإجراء الوحيد:** إشعار داخلي `_notify` لمُسنِد التكليف (`assigner`) و/أو مدير المدرسة، بمفتاح `au:<version>:task:<id>:<date>` (مرة يوميًا كحد أقصى لكل تكليف).
- **لماذا هي آمنة:** لا مال، لا واتساب، لا Webhook، لا تغيير حالة أو بيانات؛ القاعدة معطلة افتراضيًا؛ تُختبر بالمحاكاة؛ يعتمدها مدير النظام.
- **لماذا لا تكرر الموجود:** `adm_daily_reminders` يذكّر **المكلَّف قبل يوم** فقط؛ لا يوجد إشعار للمُسنِد بعد التأخر (يُعاد التحقق قبل البناء من شاشة التكليفات).
- **التشغيل:** ضمن `rikaz-homework-tick` القائم، بلا مهمة cron جديدة.
- **معايير قبول الشريحة:** (1) لا إشعار دون قاعدة معتمدة نشطة؛ (2) المحاكاة تعرض المستلمين بلا أي صف في `notifications`؛ (3) تشغيلان متزامنان = إشعار واحد؛ (4) الإيقاف الطارئ يمنع التنفيذ؛ (5) لا مستلم خارج المدرسة؛ (6) غير المالك لا يعتمد ولا يفعّل؛ (7) اختبارات الإدارة المدرسية القائمة تبقى ناجحة.

## 10. المخاطر والاعتماديات والمتطلبات

**المخاطر**
- ازدحام الإشعارات للمستخدمين → cooldown + حد يومي لكل مستلم + ملخص يومي لاحقًا.
- إبطاء الشاشات عبر triggers → فحص exists مفهرس وإدراج واحد فقط، والمعالجة خارج المعاملة.
- تجاوز مسارات الاعتماد → قائمة إجراءات مغلقة، والإجراءات الحساسة «اقتراح» فقط.
- `mt_alerts_tick` يستغرق ~1.1 ثانية — لا يُلحَق المحرك بها.
- قاعدة الاختبار تحوي منظمات اصطناعية كثيرة؛ أرقام الأداء على الإنتاج قد تختلف.

**الاعتماديات**
- اعتماد هذه الخطة.
- قرار المستخدم بشأن زمن الاستجابة (15 دقيقة مقبولة أم مهمة كل 5 دقائق = 288 تشغيل/يوم).
- لا اعتماد على وافق أو واتساب أو API الخارجية في المراحل 2–7.

**المتطلبات التقنية**
- pg_cron (متاح)، pgcrypto (متاح). لا pg_net للأتمتة الداخلية.
- لا أسرار جديدة في المراحل 2–7.
- migrations إضافية فقط على قاعدة الاختبار، ثم نسخة احتياطية موثقة وموافقة قبل الإنتاج.

**نقاط عدم يقين**
- لم يُتحقق من أن واجهة التكليفات لا ترسل تنبيه تأخر للمُسنِد بطريقة أخرى غير `notifications` (مثل شارة حمراء فقط).
- `sections` (185 صفًا) ودليل الصلاحيات (58 قسمًا بمنح) ودليل التغطية (101) مصادر متقاربة غير متطابقة؛ يحتاج دليل الأحداث ربطًا بالمصدر الصحيح (`perm_catalog`) عند البناء.
- إرسال واتساب الآلي غير مجدول حاليًا؛ أي أتمتة خارجية مستقبلية تمر عبر `message-worker` وقيوده، وليس عبر هذا المحرك.
