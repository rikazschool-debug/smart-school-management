# خدمات دخول تطبيق ركاز — نسخة مراجعة فقط

## المصدر والحالة الفعلية

- مصدر الجوال: `rikazschool-debug/rikaz`، الإصدار `4151a6900767244bed0241b7ef5e45de3e1d8274`، الحزمة `docs/vps-auth-overlay` والتعليمات `docs/VPS_CONNECTION.md`.
- قاعدة الدمج: `smart-school-management` عند `e0d66d18aaad9c8acb7aec77666f0598b7bf9e30`؛ هي أيضًا نسخة التطبيق الفعلية على VPS وقت الفحص، والحاوية سليمة. مصدر التطبيق الداخلي `127.0.0.1:3100` فقط.
- لا نشر أو ترحيلات أو تغيير أسرار أو صلاحيات أو إرسال فعلي في هذه المراجعة. لا تعديل لمشروع الجوال أو إعداداته، وتبقى `EXPO_PUBLIC_MOBILE_ID_LOGIN=0`.
- لا اعتماديات جديدة ولا تعديل لقفل الحزم. دوال `_idl_issue`, `_idl_verify`, `_idl_portal_ok`, `_idl_student`, `_idl_student_finish`, `_idl_mark_sent`, `_rk_delivery_identity`, `_rk_register_id_otp` موجودة فعليًا على VPS، واستدعاؤها مقصور على `service_role`؛ فُحص تعريفها وصلاحياتها فقط دون تنفيذها.

## ما دُمج وما حُفظ

- لم تُستبدل خدمة الدخول بنسخة الجوال. استُخرجت أجسام الدوال والمساعدات من ملف الويب **الحالي** إلى `src/lib/id-login.server.ts`، وتُستدعى من واجهة الويب الحالية ومن خدمات HTTP الثلاث.
- أُبقيت مدققات الويب ومخرجاته كما هي، بما فيها البوابة الافتراضية للويب. تحقّق محلي بمقارنة البنية النحوية من تطابق أجسام الدوال الثلاث ومساعداتها ومدققاتها قبل الاستخراج وبعده.
- حُفظ تحقق البوابة قبل الإرسال وبعد OTP، ومعرّف تسليم كل بيئة، والتسجيل قبل استدعاء WATI، وحالة الإرسال غير المؤكدة دون إعادة محاولة تلقائية، والرمز لمرة واحدة لحساب موجود. لا إنشاء حساب أو مزود إرسال جديد.
- أُضيفت طبقة HTTP من الحزمة مع ملاءمة TypeScript الصارم، و`Allow: POST`، وتطابق الأصل مع `RIKAZ_PUBLIC_ORIGIN` الموجود خلف Nginx. لا تُوثق ترويسات forwarded الواردة من العميل.
- HTTP يقبل JSON حتى 2048 بايت فعليًا، وحقولًا محددة فقط، وبوابة صريحة `staff` أو `guardian`؛ لا اختيار حساب أو مؤسسة أو دور من الطلب. لا CORS عام أو أخطاء قاعدة مفصلة أو تخزين استجابات الدخول.

## حسم بيانات الطالب

`csmart` هو **رقم الطالب الداخلي** المطابق لـ`students.csmart_no`، مع رقم الهوية/الإقامة. ليس كلمة مرور Supabase ولا PIN جديدًا. هذا مثبت من نموذج الويب ومن تعريف `_idl_student` الفعلي على الإنتاج. الدالة تستخدم `_csmart_exact` للمطابقة، مع الحفاظ على الأصفار وحالة الأحرف؛ ترفض السجل غير النشط أو التطابق غير الوحيد، وتستخدم حد المحاولات الحالي. لا نعكس هندسة كلمة مرور ولا نغيّر اعتماد الطالب.

الطالب ذو الحساب القائم يحصل بعد المطابقة وإنهاء إعداد الحساب القائم على `hashed_token` لمرة واحدة. الجوال يستبدله عبر `https://api.kalmalki.com/auth/v1/verify`، ثم يقرأ العضويات والبيانات بجلسة المستخدم وRLS. لا تُستخدم خدمة HTTP العامة لإعطاء صلاحيات إدارية.

## المسارات والتوجيه

كل المسارات التالية على **أصل التطبيق** `https://app.kalmalki.com`:

| المسار | طلب POST | النتيجة عند النجاح |
|---|---|---|
| `/api/public/auth/request-code` | `nid`, `portal` | `challenge`, `masked` فقط |
| `/api/public/auth/verify-code` | `challenge`, `code`, `portal` | `token` لمرة واحدة |
| `/api/public/auth/student-login` | `nid`, `csmart` | `token` لمرة واحدة |

خدمات Supabase تبقى على `https://api.kalmalki.com` منفصلة عن هذه الخدمات. لا فتح لـ`/api/public/auth/send-sms` أو مسارات إدارة Auth، ولا تغيير للمفتاح العام أو أسرار الإنتاج.

**عائق التوجيه الحالي مثبت:** كتلة HTTPS للتطبيق في `/etc/nginx/sites-enabled/rikaz-domains.conf` تحتوي `location ^~ /api/public/ { return 503; }`، مع استثناءات قائمة للخدمات المعتمدة. GET للمسارات الثلاثة أعاد 503 من الخارج. لا يكفي نشر كود routes وحده.

جُهزت ثلاثة ملفات مراجعة في `infrastructure/vps-app/mobile-auth/`، لا تُثبّت تلقائيًا:

1. `nginx-rate-limit.conf`: منطقة طلبات مستقلة في سياق `http`؛ 20 طلبًا في الدقيقة لكل مصدر مع burst قدره 5 في مسار الوكيل. المستخدمون خلف NAT يتشاركون الحد؛ تُراجع استجابات 429 قبل تعديل الحد.
2. `nginx-proxy.conf`: مقتطف وكيل محلي إلى `127.0.0.1:3100`، حد 2KB، مهلات محدودة، دون cache أو فتح منفذ.
3. `nginx-locations.conf`: ثلاثة استثناءات **exact فقط** داخل كتلة HTTPS للتطبيق. تبقى كتل المنع العامة والخدمات القائمة دون تغيير.

الحد الطرفي يكمّل حدود SQL القائمة: طلب OTP واحد لكل 60 ثانية وبحد 3 في 15 دقيقة، وانتهاء بعد 5 دقائق، وحد 5 أخطاء للتحقق/دخول الطالب. لا يُعامل IP كإثبات هوية. لم يُطبّق المقتطف على Nginx الفعلي؛ يلزم اختبار `nginx -t` مع كامل إعداداته المحفوظة عند اعتماد النشر.

## الفحوص وحدود القبول

- اختبارات حدود HTTP: المدخلات، البوابات، الحقول الزائدة، الحجم الفعلي، الطرق، المصدر، الأصفار وحالة الأحرف، إخفاء حقول الحساب والأخطاء وعدم تخزين الردود.
- اختبارات الخدمة المشتركة بمزوّد وقاعدة وهميين: رفض انتهاء/إعادة استخدام/حظر OTP، منع إصدار جلسة لبوابة خاطئة، حفظ تسجيل WATI قبل الإرسال، وعزل المرجع وحالة unknown، وعدم إنشاء حساب.
- اختبارات رجوع الويب: نفس المدققات ونفس المساعد المشترك. اختبار التشغيل المعزول يطلب المسارات الثلاثة بمدخلات مرفوضة فقط، بلا قاعدة أو اعتماد مزود.
- الفحص الكامل القائم في GitHub يبني Node الخاص بـVPS وCloudflare الخاص بـLovable، ويشغّل TypeScript والاختبارات وإعادة بناء مخططي القاعدة داخل بيئة معزولة لا تصل للقاعدتين. لا تعني إعادة بناء المخطط تطبيق ترحيلات حقيقية.
- يلزم بعد اعتماد النشر اختبار فعلي منفصل بحساب طالب موجود ومصرّح به وحساب ولي أمر/موظف وجوال اختبار، مع موافقة على إرسال OTP. لا يُنشأ حساب حقيقي ولا يُستخرج OTP من القاعدة لهذا الاختبار. خدمات الدخول ليست منشورة الآن.

## خطة النشر بعد اعتماد مستقل

1. اعتماد commit محدد بعد نجاح جميع فحوص فرع المراجعة. إعادة مقارنة نسخة الإنتاج ومصدر الويب إن تغيّر أي منهما؛ عدم نشر مصدر قديم فوق تعديل أحدث.
2. حفظ اسم صورة التطبيق الجارية ونسخة محمية من إعداد Nginx الحالي والمقتطفات ذات الصلة. مراجعة فرق يفتح المسارات الثلاثة فقط؛ لا تعديل قاعدة أو أسرار أو إعداد تكامل أو طابور.
3. استخدام بوابة النشر القائمة لصورة التطبيق الجديدة؛ لا إنشاء مسار نشر بديل أو تشغيل أوامر `compose down`. لا توجد ترحيلات جديدة في هذه الحزمة. إثبات صحة الصورة قبل فتح المرور.
4. تثبيت المقتطفات الثلاثة في مواضعها المشار إليها، مع إبقاء كتلة التطبيق وبقية المواقع والخدمات القائمة. تشغيل `nginx -t` قبل reload، والتوقف إذا فشل. هذه خطوة إعداد مراجعة مستقلة؛ المشغّل الحالي لا يثبت ملفات Nginx تلقائيًا.
5. قبول خارجي دون إرسال: GET=405 و`Allow: POST`، JSON ناقص=400، نوع غير مسموح=415، مصدر غير موثوق=403، والحجم الزائد=413 من Nginx أو 400 من حد التطبيق. فحص `/auth` والخدمات الحالية ومنع `send-sms` والمسارات الداخلية.
6. بعد إذن الاختبار الفعلي: OTP مرة واحدة إلى الجوال المحدد، ثم دخول ولي الأمر/الموظف؛ طالب موجود بالهوية وC-Smart؛ استبدال token عبر Auth VPS وقراءة العضويات والصلاحيات ومقارنة نطاق المدرسة بالويب ورفض الوصول خارج النطاق. لا تسجيل token أو OTP أو بيانات أشخاص في تقارير التشغيل.
7. يبقى علم الجوال 0 حتى نجاح هذه الخطوات؛ عندها فقط يُراجع تفعيله إلى 1 في إصدار الجوال. لا تنسخ إعدادات السحابة إلى الإنتاج.

## الرجوع

عند فشل فتح HTTP: أعد إعداد Nginx المحفوظ، نفّذ `nginx -t` ثم reload، فترجع المسارات الجديدة إلى المنع. أعد صورة التطبيق السابقة عبر إجراء الرجوع القائم إن كان الفشل من الصورة؛ واجهة الويب السابقة ودوال القاعدة لم تتغير. أعد/أبقِ علم الجوال 0. لا restore أو reset أو عكس ترحيلات أو حذف بيانات/volumes أو تغيير مفاتيح أو تشغيل طوابير قديمة. توقف عند أول فشل وسجّل هل تبدلت الصورة وهل فُتح التوجيه، دون ادعاء نجاح الدخول الفعلي.
