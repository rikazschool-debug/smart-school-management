# معاينة Expo Web على Replit — تغيير للمراجعة قبل النشر

## السبب المثبت ونطاق الفحص

- المعاينة التي قدّمها المستخدم: `https://de465eba-d58f-4044-a96f-e509a0f51668-00-2hirn3vv6u77u.expo.sisko.replit.dev/`؛ السماح للأصل فقط، دون `/` أو مسار أو معاملات.
- فحص HTTPS الخارجي للمسارات الثلاثة الحالية، باستخدام هذا Origin وطلب POST و`Access-Control-Request-Headers: content-type`، أعاد OPTIONS=405 و`Allow: POST` دون أي ترويسات CORS. هذا يمنع المتصفح من إرسال طلب JSON التالي.
- HTML وحزمة JavaScript الفعلية للمعاينة أعادا 200؛ `callPlatform` يستعمل POST مع `Content-Type: application/json` و`Accept: application/json` دون credentials أو Authorization. `Accept` ترويسة آمنة لا تحتاج إضافة إلى Allow-Headers؛ المطلوب Content-Type وحده.
- الإنتاج عند الفحص هو صورة `c3b14b15f3e991146e7169c6d5202cca49d59723`، سليمة. فرع المراجعة بدأ من main عند `080d95659ed557a93004638f4278305bee3669b2`؛ ملفات دخول الجوال وتوجيه Nginx متطابقة بينهما. توجد تعديلات أخرى في main؛ هذا التغيير لا يعتمد نشرها تلقائيًا.

## التغيير المحدد

في طبقة HTTP الخاصة بـ`request-code` و`verify-code` و`student-login` فقط:

- مقارنة Origin بالنص الكامل المعتمد، دون `*` أو مطابقة suffix/نطاق Replit كامل أو الثقة بترويسات forwarded.
- OPTIONS المطابق للأصل وPOST والترويسة Content-Type يعيد 204 وجسمًا فارغًا، قبل قراءة جسم الطلب أو تحميل وحدة الدخول أو استدعاء قاعدة/مزود إرسال.
- ترويسات النجاح: `Access-Control-Allow-Origin` للأصل المحدد، و`Access-Control-Allow-Methods: POST` و`Access-Control-Allow-Headers: Content-Type`؛ لا Allow-Credentials ولا Expose-Headers ولا Max-Age.
- أي أصل آخر أو طلب طريقة/ترويسة غير معتمد في preflight يعاد 403 دون ترويسات سماح. OPTIONS غير المرتبط بالمعاينة يحتفظ بسلوك المنع القائم.
- POST من المعاينة يستمر عبر جميع المدققات الحالية وخدمة إثبات الهوية نفسها؛ استجاباته، بما فيها أخطاء التحقق، تحمل أصل المعاينة حتى يستطيع المتصفح قراءتها. كل الاستجابات no-store مع Vary مناسب.
- تحميل `id-login.server` أصبح كسولًا بعد نجاح التحقق. الدخول الأصلي Native دون Origin والويب من أصل الموقع يظلان على المسار القائم.

لا تعديل لدوال الدخول المشتركة أو جداول أو ترحيلات أو صلاحيات أو أسرار أو ملفات اعتماديات. لا تعميم CORS على Supabase أو server functions أو بقية `/api/public/`.

## حدود الحماية

CORS حد للمتصفح، وليس بديلًا للتحقق من الهوية أو حد محاولات الدخول. العميل غير المتصفح يستطيع تكوين Origin أو حذفه؛ الإثبات الحالي والحدود يبقيان مطلوبين. السماح بأصل المعاينة يتيح لكود هذا الأصل قراءة نتائج دخول يطلبها، لذلك يجب استبدال/إزالة هذا الإدخال بمراجعة عند تغير المعاينة أو انتهاء الاختبار.

حدود Nginx القائمة (20 طلبًا/دقيقة، burst=5، جسم 2KB والمهلات) لا تتغير وتشمل OPTIONS. أخطاء Nginx المباشرة مثل 429/413 تظل بحمايتها الحالية وقد يعرضها المتصفح كخطأ اتصال عام لغياب CORS عنها؛ لا نضيف سياسة عامة ثانية في Nginx ولا نعفي preflight من حدود الطلبات.

## الفحص والنشر اللاحق

1. اختبارات محلية بخدمات وهمية فقط: الأصول والطرق والترويسات المسموحة/المرفوضة، عدم تحميل خدمة الدخول في OPTIONS أو الإدخال المرفوض، المدققات ومخرجات DTO والأخطاء، وNative والويب القائم.
2. فحص التطبيق المبني في حاوية معزولة بلا شبكة عبر مشغّل الفحص القائم: preflight لكل مسار، رفض الأصل الآخر والترويسات الزائدة، POST فارغ=400، وعدم امتداد السماح إلى send-sms أو تجاوز CSRF للويب. لا رموز أو حسابات حقيقية.
3. قبل أي نشر، اعرض فرق الملفات ونتائج الفحص واعتمد إصدارًا محددًا عبر الآلية القائمة؛ لا نشر ضمن هذا الطلب، ولا تغيير Nginx أو قاعدة أو أسرار. يلزم مراجعة التغييرات الأخرى المتراكمة في main قبل اختيار الإصدار.
4. بعد اعتماد النشر مستقبلًا: أعد OPTIONS الخارجي من الأصل الفعلي والمتغير غير المسموح، ثم طلب JSON ناقص فقط، وفحص صحة الموقع. اختبار دخول حقيقي أو إرسال OTP يحتاج طلبًا منفصلًا من المستخدم. يبقى `EXPO_PUBLIC_MOBILE_ID_LOGIN=0` في هذه المرحلة.
5. الرجوع بإصدار التطبيق السابق عبر الآلية القائمة يعيد سياسة الأصل السابق؛ لا ترحيلة أو إعادة ضبط أو استعادة بيانات أو عكس قاعدة. لا يوجد cache preflight طويل يؤخر إزالة السماح.

## نتائج الفحص قبل رفع المراجعة

- اختبارات الدخول وCORS الأربعة: **81/81 ناجحة**، بخدمات وهمية فقط. TypeScript بلا أخطاء.
- اختبار HTTP محلي لطبقة المعالجة نفسها، على المسارات الثلاثة: الأصل المحدد OPTIONS=204، أصل مرفوض OPTIONS=403 بلا ترويسات سماح، POST فارغ=400 مع CORS للأصل المحدد؛ عدد تحميلات خدمة الدخول صفر. هذا ليس اختبار تشغيل TanStack/Nginx المبني.
- فحص المشروع العام على Windows/Bun: 626 ناجحًا، 8 اختبارات اختيارية متجاوزة، وفشلان في اختبارات صلاحيات collaboration. طُوبق الفشلان مع فحص main السابق على GitHub [44183352402](https://github.com/rikazschool-debug/smart-school-management/actions/runs/44183352402)، قبل أي تعديل CORS. توجد أيضًا ثلاث مجموعات تعذر تحميلها تحت Bun بسبب `z.object`/`z.string`؛ لا تُحسب اختبارات ناجحة.
- بناء VPS المحلي أكمل مرحلتي المتصفح وSSR، ثم توقف عند تجميع Nitro بسبب `EPERM: readlink C:\Users\REFAAT` في بيئة Windows المقيدة. لا يُعتبر نجاح بناء كاملًا أو اختبار تشغيل للنسخة المبنية.
- فحص Linux عبر مسار GitHub القائم موضع تتبع المراجعة. الفحوص العامة الفاشلة تمنع اعتبار إصدار main جاهزًا للنشر؛ لا يُتجاوز الحاجز ولا تُعدّل الصلاحيات لإخفاء الفشل. اختبار التشغيل المبني/بناء Lovable يبقيان غير مثبتين لهذا التغيير إذا توقف المسار قبل الوصول إليهما.
