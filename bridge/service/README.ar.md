# خدمة ADMS الدائمة — الإصدار 2

المرجع التعاقدي هو `../../ADMS-RAKAZ-INTEGRATION.md`. هذا الإصدار يجعل لوحة الجسر مصدر المواقع والأجهزة، ويلغي الاستيراد الإداري من ركاز. لا تغييرات في تطبيق ركاز أو قاعدة إنتاجها.

Node 24 المثبت على الخادم يدعم `node:sqlite` دون اعتماديات npm. التشغيل: `node adms-bridge.mjs` مع `BRIDGE_CONFIG` لملف خادمي محمي. ملفات example تحتوي وصفًا فقط ولا تصلح للتشغيل المباشر. حافظ على اسم مستخدم الإدارة وبصمة كلمة مروره الحالية، ولا تولد مفاتيح جديدة عوض الموجودة تلقائيًا.

## الترحيل

إنشاء `Store` يطبق ترحيل SQLite رقم 2 داخل معاملة واحدة بعد نسخة احتياطية متسقة. الجداول الأصلية السبعة تبقى دون حذف أو تعديل. تُضاف جداول `bridge_*` ومؤشر `bridge_schema`. إن وجدت بيانات قديمة، تنقل معرفات المؤسسات والمواقع والأجهزة كما هي، والتاريخ إلى سجلات v2 مع `legacy_event_id/legacy_ref`. المحاولات والطابور القديمان محفوظان في جداول v1. حالات التسليم القديمة الناجحة تبقى ناجحة، وسائر القديم يوضع في `held/legacy_review_required` دون إعادة إرسال. الربط الصريح `school_id` إن وجد يحفظ كمعرّف موقع وعلامة legacy_school_id؛ لا يُخمن ربط مفقود. المواقع المستوردة محلية غير مفعلة حتى مراجعتها. تضارب التسلسلي يعلّم legacy_conflict ويمنع الاستقبال والتفعيل، دون دمج أو حذف الجهاز.

لا تستخدم `import-snapshot`: الأمر مرفوض صراحة. لا توجد ترحيلات Supabase في هذا التغيير.

## العمليات المقصودة لاحقًا فقط

إضافة مؤسسة وموقع وجهاز من اللوحة لا تفعّل استقبالًا. يتطلب الجهاز credential محليًا محفوظًا، ومصدرًا شبكيًا موثوقًا، ومطابقة تسلسلي، والتحقق من دعم النقل الفعلي. لا تنشر مقبس intake للعامة قبل ذلك.

تجهيز مفتاح قراءة مستقل يتم من SSH بـ`ops/credentials.py registry-key /root/approved-key-request.json`؛ ملف الطلب يحمل org_id وkey_id غير سريين. الأداة مولّدة أسرار root-only لا تطبعها، ولا تفعّل استقبالًا أو إرسالًا. الأمر `revoke-key` يبطل مفتاح القراءة بعد تحميل الملف من جديد. بعد تعديل ملف سر مركّب، أعد إنشاء حاوية الجسر وحدها لتحميله؛ أرسل ملف الاعتماد عبر قناة آمنة إلى إعدادات خادم ركاز، وليس متصفحها أو المحادثة.

تدوير القراءة: مفتاح جديد بمعرّف جديد للمؤسسة نفسها، تحميل الخادم، نقل السر الجديد بطريقة آمنة إلى خادم ركاز، اختبار health/sync، إبطال القديم وإعادة التحميل ثم اختبار رفضه. تدوير التسليم: أوقف التسليم، جهّز مفتاحًا جديدًا، وافق على ثقة الخادم المستقبِل، استبدل المفتاح في الطرفين دون نشره، اختبر بعزلة ثم أعد التفعيل الصريح. لا تخزن الأسرار في Git أو السجلات.

الموافقة على نطاق إرسال مستقبلي: `node cli.mjs approve-scope /run/secrets/approved-scope.json` داخل الحاوية، بملف محمي يحمل org_id وrikaz_org_id وsite_id وdevice_id وfrom وقت UTC حاليًا/مستقبلًا؛ لا يسمح بتاريخ ماض ولا ينشئ طابورًا للتاريخ القديم. هذا يربط النطاق فقط، ويبقى global delivery disabled حتى اعتماد تفعيل مستقل. ضبط مفاتيح التسليم عبر `ops/credentials.py delivery-key` ينشئ إعدادًا enabled=false؛ طلبه يتضمن receiver_url وrikaz_org_id مطابقين للربط المراجع. راجع مخطط المفاتيح بالمواصفات. لا تنفذ هذه الأوامر الآن على جهاز أو مؤسسة وهمية.

## التراجع

بعد أخذ نسخة DB متسقة، التراجع عن الشيفرة وملف Nginx الخاص بالحضور يكفي لعودة v1 في المرحلة الحالية؛ تُترك جداول v2 دون حذف لحفظ أي بيانات أضيفت. لا تستبدل قاعدة البيانات كاملة تلقائيًا إذا ظهرت حركات أو تغييرات جديدة. v1 لا يعرض سجلات v2 الجديدة؛ عند وجودها يلزم وقف كتابة متفق عليه ومراجعة/تصدير محلي محمي قبل أي استعادة. ملفات القاعدة والأسرار والنسخ الاحتياطية خارج Git.


## إعدادات توصيل الجهاز (2.0.1)

قسم اللوحة يقرأ GET /manage/api/devices/{id}/connection بالمصادقة الإدارية الحالية. يسجل evidence خادميًا تحت config.device_connection_evidence، مربوطًا بـUUID والتسلسلي والموديل وFirmware. تعاد settings=null حتى تتأكد الميزة وطريقة توثيق يدعمها الجهاز وتجربة المستقبِل الخارجية الحديثة وتفعيل intake. لا يغير الطلب آخر اتصال ولا القوائم ولا الطوابير، ولا يظهر أي سر. حالات العائلة العامة/صور Ethernet لا تعني أن جهازًا بعينه يدعم ADMS أو HTTPS. القيم المختبرة على محاكي ليست قيمًا معتمدة لجهاز فعلي. لا توجد طريقة SN-only جديدة، ولا دعم مزعوم لترويسات مخصصة في MB10/ID. مسار native ADMS أو وسيط بديل ينتظر إثبات دعم الجهاز واعتماد النقل؛ لا تفعلها بتغيير evidence يدويًا فقط.

## الاستقبال المباشر عبر الإنترنت — تحديث 2026-11-12

نقطة الخادم: `attendance.kalmalki.com:443` عبر HTTPS. اسم النطاق مشترك؛ لا يُفترض دعم HTTPS في كل جهاز ADMS. منفذ 80 لا يستقبل حركات، ولا علاقة للمنفذ 4370 بمنفذ ADMS. لا VPN ولا وسيط أو تغيير راوتر ضمن التصميم.

الحماية المتاحة للأجهزة الأصلية دون ترويسات خاصة: HTTPS مع اعتماد عنوان الإنترنت العام للموقع كـ IPv4 /32، ثم ربط SN بالسجل والموقع وepoch الحاليين. يفرض Nginx قائمة سماح فارغة افتراضيًا، ويستبدل جميع ترويسات إثبات النقل والمصدر، ويضيف سرًا داخليًا غير معروف للجهاز. يعيد التطبيق التحقق مستقلًا عبر Unix socket خاص. بيانات إدارة اللوحة لا تمنح حق إرسال حركات.

**حد الحماية:** جهاز آخر خلف عنوان الإنترنت العام نفسه قد ينتحل SN. هذا اعتماد لشبكة الموقع وليس مصادقة تشفيرية لكل جهاز. لا يُعتمد جهاز حقيقي حتى توثيق ADMS وHTTPS والتحقق من شهادة الخادم، وتحديد عنوانه العام الصحيح، وقبول هذا الحد للتجربة المحلية. لا يُفترض أن Comm Key أو Bearer/HMAC أو mTLS متاح؛ المصادقة الأصلية الإضافية تحتاج وثيقة لهذا الإصدار واختبارًا. إذا لم يثبت HTTPS أو حماية أصلية مناسبة، يبقى الاتصال المباشر مغلقًا وتُراجع الخيارات مع المستخدم قبل إضافة بنية أخرى.

مراحل التوصيل اللاحقة: تسجيل الجهاز الحقيقي في المؤسسة/الموقع، توثيق شاشة ADMS/HTTPS وPushComm إن ظهر، اعتماد مصدره وحماية الاتصال في ملفات الخادم، توليد قائمة Nginx من المصادر المعتمدة واختبارها قبل reload، ثم تحديث الربط في ملف config وإعادة إنشاء خدمة الجسر لتحميل ملفات bind المركّبة بعد استبدالها الذري. لا يكفي تعديل ملف بيانات الدخول ولا إضافة سجل جهاز إداري. لا يصدر هذا الإصدار مفاتيح تلقائيًا للجهاز ولا يغير إعداداته.

تعرض اللوحة إعدادات الخادم المختبرة منفصلة عن حالة الجهاز. إذا كانت حقول Address وPort منفصلة: النطاق دون بروتوكول و443؛ إذا جمعت الشاشة المنفذ مع النطاق تُراجع صيغتها أولًا. Domain Name=ON عند دعمه وHTTPS=ON بعد إثباته فقط. يلزم Gateway حقيقي وDNS متاح من شبكة الجهاز، دون افتراض عنوان راوتر أو شبكة الحاسوب.

`storage_only=true` يمنع إنشاء أي `bridge_outbox` من الحركات المستقبلة في هذه المرحلة، حتى مع اعتماد نطاق سابق. و`delivery_enabled=false` و`delivery_url=null` وDocker `network_mode: none` تمنع الإرسال أيضًا. ACK بعد الحفظ الدائم فقط؛ إعادة إرسال الصف نفسه لا تنشئ حركة ثانية. لا تحويل تلقائي للسجلات المحلية القديمة إلى طابور ركاز.

يجب أن تتطابق `keys.devices[device_id]` عند اعتماد جهاز لاحقًا مع: `ingest_mode=https_source`, `site_id`, `device_epoch`, `allowed_sources` بعناوين /32 فقط، وإثباتات `source_approved`, `adms_verified`, `device_https_verified`, `shared_network_risk_accepted`. وتظل ملفات config/keys والسر بين Nginx والتطبيق خارج Git وبصلاحيات محمية. قائمة السماح في Nginx لا تغني عن الربط لكل جهاز داخل التطبيق. قائمة السماح الفعلية فارغة حتى استكمال إثباتات أول جهاز؛ لا تضع عناوين نموذجية فيها.

## MB2000 بصيغة IP وبورت منفصل — 2026-11-12
ظهرت وحدة MB2000/ID BRC7230660331 في صور المستخدم مع ADMS، ثم رُصدت طلبات فعلية تحمل SN نفسه وPUSH 2.4.1 وHTTP/1.1. هذا يثبت النقل الحالي ولا ينفي احتمال وجود TLS في خيارات/إصدار آخر. اختبارات TLS على IP الحالي فشلت؛ لا يعتمد IP:443 لهذه الوحدة.

أضيف مسار منفصل: 2.25.3.1:80 عبر HTTP، Domain Name=OFF وProxy=OFF، مقيّد بمصدر الوحدة المرصود. قيمة `ip_adms.accept_records=false` و`unencrypted_risk_accepted=false` تبقيان الحفظ والإقرار متوقفين؛ لا تولد طلبات 503 المرفوضة آخر اتصال ناجح. لم يوافق المستخدم بعد على الحفظ عبر نقل غير مشفر. لا تفعّل الحفظ تلقائيًا بسبب ظهور صور/طلب تغيير IP أو فشل HTTPS.

إذا وافق المستخدم لاحقًا صراحةً على تجربة محدودة غير مشفرة، يشترط تفعيل العلمين مع `approved_at` و`expires_at` بفارق لا يتجاوز 1800 ثانية، وبقاء storage_only=true والتسليم متوقفًا وdelivery_url=null. يفحص الزمن مرة أخرى بعد قراءة الطلب؛ انتهاء المهلة يوقف الإقرار والحفظ دون حذف سجلات. قواعد IP لا تعادل توثيق جهاز مستقل، وخاصة خلف NAT مشترك. تبقى تجربة HTTP خيارًا منفصلًا، بلا fallback تلقائي وبلا VPN أو وسيط.

لم يغير هذا العمل سجل الجهاز الذي عدله المستخدم في اللوحة إلى المدرسة/MB2000، أو وجهة جهاز ميداني. القيم القديمة الظاهرة في الصورة 8.213.41.71:30022 لبرنامج فعّال وفق المستخدم؛ يلزم ترتيب التجربة والرجوع معه. لا اختبار أو اتصال بالخادم القديم.

أُضيفت تجربة HTTP معزولة بإذن المستخدم بتاريخ 2026-11-12. جلسة مستقلة بقاعدة SQLite تحت /data/http-trials: أرشيف لما سبق وقت البداية، مرشحات داخل النافذة، وأوقات غير صالحة للمراجعة. لا تدخل جداول الحضور العادية ولا طابور ركاز. لا تعدّ المرشحات بصمات اختبار مؤكدة حتى مطابقة PIN والوقت وعدد المحاولات مع المستخدم. يدعم تأكيد أكثر من سجل عندما يؤكد المستخدم أكثر من محاولة؛ لا تدمج أوقاتًا مختلفة باسم منع التكرار.

يُحفظ النص الخام لـATTLOG داخل ملف التجربة المحمي. الدفعات التي لا يمكن تحليلها تُحجز دون ACK، مع تجميع التكرار حسب SHA؛ بعد تصحيح التنسيق تبقى نسختها الأصلية ويُعلّم حلها بالحفظ الناجح دون حذفها. أظهرت وحدة MB2000 الفعلية PUSH 2.4.1 أنها تضيف tab فارغًا بعد حقولها العشرة؛ تُهمل الحقول الفارغة النهائية في الهوية المنطقية مع إبقاء النص الأصلي. ما عدا ذلك تظل هوية الصف الكامل الدقيقة، والأوقات المتجاورة المختلفة لا تُدمج.

تجربة المستخدم الفعلية كانت نافذتها 2026-11-12 13:44:45 إلى 14:14:45 بتوقيت الرياض. أكد المستخدم لاحقًا محاولتين في الدقيقة 13:51، وطابقتا سجلين عند 13:51:20 و13:51:21 للمستخدم المطلوب. إثبات إعادة السجلين المطابقين جرى على نسخة متسقة معزولة بلا شبكة، لا بإرسال حضور مصطنع إلى الجهاز أو الإنتاج. حالة الإغلاق النهائية ونتائجها تُسجل في تقرير التنفيذ المنفصل.

الإغلاق يجمع فحص مهلة كل طلب مع مؤقت systemd دائم AccuracySec=1s يعطل قبول الحركات ويستبدل ACL بقائمة deny all، ثم يعيد تحميل الخدمة ويأخذ نسخة متسقة. لا يعيد ضبط وجهة الجهاز تلقائيًا، ولا يصدر أوامر مسح أو تحديث Firmware أو ضبط الساعة. تظل بيانات التجربة محفوظة بعد الإغلاق ولا ترحّل تلقائيًا إلى ركاز.

## تشغيل الأجهزة من اللوحة القائمة — 2.3.0، 2026-11-12
هذا القسم يحل محل خطوات الاعتماد اليدوي لكل جهاز في الأقسام التاريخية أعلاه. لا قوائم أو جداول كيانات موازية: أعمدة إضافية في bridge_sites وbridge_devices، وتدقيق في bridge_audit الحالي. الترقية تحفظ UUID والقوائم والحركات وتبدأ جميع الأجهزة القائمة باستقبال موقوف؛ التفعيل الإداري وحده لا يمنح استقبالًا.

1. سجل المؤسسة والموقع والجهاز (الموديل وSN) من أقسامها الحالية.
2. من «المواقع ← اعتماد شبكة الموقع»، أدخل IPv4 العام الفعلي لخروج الفرع، عنوانًا كاملًا لكل سطر (حتى ثمانية /32، دون عناوين داخلية أو شبكات واسعة). اعتمد حدود المصدر. التغيير أو الإلغاء يوقف استقبال أجهزة الموقع ولا يعيد تفعيلها.
3. من «إعدادات التوصيل» اختر الجهاز، وطريقة النقل التي يدعمها فعليًا، ومدة 30 دقيقة أو 24 ساعة أو استقبال مستمر حتى الإيقاف اليدوي. أكد ADMS وحدود انتحال جهاز خلف المصدر نفسه. HTTP يتطلب قبول عدم التشفير للمدة المختارة؛ HTTPS يتطلب تأكيد دعم الجهاز لشهادة النطاق واسم النطاق. الموافقات لا تؤكد توافقًا آليًا من رقم الموديل.
4. اضغط «اعتماد وتفعيل استقبال الجهاز»، ثم أدخل قيمه بنفسك في الجهاز المتوافق. HTTP: Server IP=2.25.3.1، Port=80، Domain Name=OFF، HTTPS=OFF، Mode=ADMS. HTTPS المشترك attendance.kalmalki.com:443 لا يُستخدم إلا بعد إثبات توافق الجهاز؛ لا IP:443 ولا تجاوز تحقق شهادة. Gateway/DNS الفعليان يحددهما موقع الجهاز، ولا يُفترض عنوان راوتر أو وجوده على شبكة الحاسوب.
5. راقب آخر اتصال بعد الاعتماد وآخر حركة ووقتها الخام ورقم المستخدم في «الحركات والتسليم». ACK بعد الحفظ الدائم، ومنع التكرار للصف المطابق الكامل. الأرشيف الذي يعيد الجهاز إرساله يحتفظ بوقته الخام محليًا؛ لا يُفسّر تلقائيًا كحركة اختبار جديدة. تجربة HTTP السابقة تبقى منفصلة ومغلقة، ولا تُدمج أو تُحذف.

الحماية: Nginx auth_request على المسارات الدقيقة يراجع سياسة قاعدة الجسر عبر socket خاص قبل تمرير الجسم. ترويسات النقل والمصدر مأخوذة من Nginx وسر داخلي محمي، لا من الجهاز. يتحقق التطبيق مجددًا بعد قراءة الجسم وداخل معاملة الحفظ؛ الإيقاف أو انتهاء المدة أثناء الطلب يمنع ACK والحفظ. لا reload أو تعديل config/keys/ACL لكل جهاز. managed_ingress يُفعّل مرة على الخادم بعد تجهيز مسارات Nginx ولا يسمح بالرجوع إلى اعتماد legacy/trial.

المصدر العام + SN ليس هوية تشفيرية لكل جهاز. HTTP يكشف رقم المستخدم ووقت الحركة ويمكن اعتراضه؛ HTTPS يحمي النقل عند التحقق الصحيح من الشهادة لكنه لا يمنع انتحال جهاز آخر خلف المصدر المعتمد. لا نفترض دعم مفتاح أصلي أو headers مخصصة. تغيّر IP العام يتطلب إعادة اعتماد المصدر والأجهزة من اللوحة. لا تُقبل عناوين واسعة لتجاوز هذا القيد. رفض مصدر مجهول لا يُنسب إلى جهاز من SN وحده، ولا يصبح آخر اتصال ناجحًا.

المسارات الإدارية الجديدة داخل API الحالي: POST /manage/api/sites/{id}/sources وPOST /manage/api/devices/{id}/ingress، تحت نفس Basic وOrigin وCSRF. تغيّر SN/الموديل/الموقع/الحالة الإدارية يوقف الاستقبال ويتطلب اعتمادًا صريحًا جديدًا؛ إعادة التفعيل الإداري لا تُعيد الاستقبال. أسباب الإيقاف والمهلة والنقل غير المطابق وأخطاء التنسيق تظهر في البطاقة. لا تُعرض أسرار، ولا مفاتيح أجهزة مُفترضة.

تبقى storage_only=true وdelivery_enabled=false وdelivery_url=null وnetwork_mode=none. مسار managed يحفظ محليًا دون إنشاء outbox حتى للموقع المخصص لركاز. لا تفعيل أجهزة فعلية أثناء النشر، ولا إرسال إلى ركاز أو تعديل Firmware/الجهاز أو قاعدة ركاز. تستمر نسخ main/trial المتسقة. الاستعادة من نسخة ما قبل التغيير تعيد المصدر/config/Nginx فقط مع إبقاء DB الأحدث؛ الأعمدة الإضافية آمنة للإصدار السابق، ولا يجوز استبدال حركات أحدث بنسخة قديمة.
