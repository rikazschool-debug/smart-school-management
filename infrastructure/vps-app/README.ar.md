# تشغيل ركاز على VPS مع إبقاء Lovable مستقلة

هذه الملفات تحفظ إعداد تشغيل Node للتطبيق وخادمه. لا تنقل قاعدة أو بيانات، ولا تنشر شيئًا بمجرد إضافتها أو فتح Pull Request. لا توجد workflow للنشر التلقائي هنا.

## فصل البيئتين

| الإعداد | Lovable / قاعدة الاختبار | VPS |
| --- | --- | --- |
| البناء | vite.config.ts وbuild الحاليان دون تعديل | نفس الإعداد؛ Docker يحدد NITRO_PRESET=node-server |
| المتصفح | متغيرات مشروع المعاينة الحالية | VITE_SUPABASE_URL=https://api.kalmalki.com، ومفتاح anon الخاص بنفس VPS وقت البناء |
| الخادم | إعداد الخادم الخاص بالمعاينة | SUPABASE_URL=http://api-gw:8000 على شبكة Docker القائمة، ونفس مفتاح anon مع المفتاح الخدمي وقت التشغيل فقط |
| CSRF | أصل الطلب عند غياب RIKAZ_PUBLIC_ORIGIN | أصل HTTPS ثابت مضبوط خادميًا، دون الوثوق بترويسات عميل |
| الإرسال | لا يتغير أي متغير بمشروع المعاينة | RIKAZ_OUTBOUND_ENABLED=false قبل المطالبة بطوابير الإرسال أثناء القبول |

لا تضع المفتاح الخدمي أو كلمة مرور PostgreSQL في VITE_* أو build args. لا تنسخ .env السحابي إلى إنتاج VPS. حزمة Lovable المثبتة تضبط هدفها داخل بيئتها؛ لا تضف Nitro أو TanStack أو React plugins مرة ثانية.

أُزيل استدعاء ضخ طابور الفعاليات العام من المتصفح. الدالة المتبقية لشاشة القرار no-op. هذا تغيير أمني مشترك عند دمج الفرع لاحقًا؛ لا يُدّعى الحفاظ على ضخ الرسائل القديم. يلزم عامل موثق ومحدد بالمؤسسة/الحدث قبل تفعيل التسليم، ولا يكفي قلب متغير الإرسال.

## الملفات

- Dockerfile وDockerfile.dockerignore: صور مثبتة، ملف قفل محفوظ، قائمة سماح تستبعد .env وGit والترحيلات والـseed، وتشغيل Node غير جذري منفصل عن البناء.
- compose.stage1.yml: الاسم محفوظ لتوافق المسار؛ يدير خدمة التطبيق الواحدة فقط على 127.0.0.1:3100. يلزم RIKAZ_APP_IMAGE بإصدار فريد مراجَع لتجنب إعادة وسم صورة جارية دون قصد.
- public-build.env.example وserver.env.example: قوالب فارغة للمفاتيح؛ الأول للبناء العام، والثاني للتشغيل الخاص. القيم الفعلية خارج المستودع في /etc/rikaz/app، بملكية root وصلاحية 600 ومجلد 700.
- supabase-auth.env.example: مرجع VPS فقط، وليس ملف Supabase كاملًا أو إعدادًا يطبَّق آليًا. يبقى التسجيل العام مغلقًا؛ المالك مستخدم Auth مؤكد وصف platform_admins يضاف إداريًا، لا من الواجهة.
- storage-buckets.json: مواصفات حاويات خاصة وحدودها؛ ليس seed أو ترحيلًا، ولا يكتب في قاعدة عند قراءته. تبقى السياسات الموجودة مصدر الصلاحية.
- app-location.nginx.conf.example: مرجع لجزء app الحالي دون HTTP Basic. تبقى لوحتا الإدارة مستقلتين ومحميتين.
- isolated-smoke.mjs: اختبار تغليف بحاوية بلا شبكة أو مفاتيح حقيقية؛ لا يغني عن قبول Auth/RLS/Storage المعزول.

لا تطبع ملفات الاعتماد أو docker compose config الموسع، ولا تضع بيانات دخول في التوثيق. SITE_URL والتحويلات وVault والتخزين إعدادات بيئة تُراجع مستقلًا؛ لا تستبدل ملف Supabase الكامل أو تغير مفاتيحه القائمة.

## إصدار لاحق — ليس جزءًا من فتح طلب المراجعة

بعد اعتماد نشر مستقل ومن جذر مصدر الإصدار، مع RIKAZ_APP_IMAGE جديد ونسخة رجوع محفوظة:

```sh
docker compose --env-file /etc/rikaz/app/build-public.env \
  -f infrastructure/vps-app/compose.stage1.yml build web
docker compose --env-file /etc/rikaz/app/build-public.env \
  -f infrastructure/vps-app/compose.stage1.yml up -d --no-deps web
```

تحقق أولًا من مطابقة مفاتيح البناء والتشغيل لنفس VPS واجتياز القبول. لا تستعمل compose down لمشروع Supabase، ولا تحذف volumes أو تعيد ترحيلات القاعدة. الاسترجاع بإعادة صورة التطبيق وكتلة app السابقتين دون استعادة قاعدة أو حذف بيانات.

لا يُعدل Nginx تلقائيًا. تغيير جزء app يحتاج نسخة وnginx -t وفحص HTTPS والأصول والجلسة وCSRF من الخارج. تبقى المنافذ الداخلية غير عامة.

## الاختبار دون لمس البيئتين

تعمل اختبارات الوحدة ببيانات .invalid وجلسات وهمية. بناء Node وCloudflare يستخدم متغيرات اختبار فقط، دون ملفات اعتماد أو شبكات إنتاج أو SQL/seed/ترحيلات أو مزودي رسائل. النجاح يثبت البناء والحدود المختبرة، وليس نشرًا جديدًا في Lovable أو قبولًا لكل شاشة وتكامل.

SMTP وWATI وبقية المزودين تُجهز وتُختبر وتُفعل لاحقًا. ADMS والمهام المجدولة مستقلتان عن مجرد نشر التطبيق؛ لا تُرسل سجلات حضور قديمة أو رسائل معلقة بمجرد إضافة مفتاح.
