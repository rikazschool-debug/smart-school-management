# فحص واعتماد إصدارات ركاز

هذه إضافة لمسار VPS الحالي، وليست مسار تطبيق أو قاعدة بيانات جديدًا. ملفات التطبيق وDockerfile وCompose والترحيلات القديمة باقية كما هي. لا ينشر حفظ Lovable أو push إلى main شيئًا على VPS. هذا الفرع للمراجعة؛ لا تدمجه بوصفه موافقة على نشر التطبيق.

## رحلة الإصدار بعد استكمال التهيئة

1. عدّل واختبر في Lovable على مشروع السحابة `czoaudsfbinpkwqsmhrd`. يصل الكود إلى GitHub عبر المزامنة القائمة. عند تغيير البنية اطلب ملفًا جديدًا داخل `supabase/migrations`؛ تعديل قاعدة السحابة وحده لا يُنشئ ملفًا تلقائيًا ولا يصلح للنشر.
2. في GitHub افتح **Actions → فحص إصدار ركاز**. الفحص التلقائي للكود والترحيلات لا يملك اعتماد الإنتاج. اختر عملية ناجحة على **main** تخص الإصدار المطلوب، وافتح تقريرها وملف `release-candidate`. يظهر SHA كامل ثابت، وبصمات الترحيلات، والمخاطر. رقم العملية في آخر رابط `/actions/runs/<رقم>` هو رقم الإصدار المرشح الذي ستختاره.
3. افتح **Actions → اعتماد ونشر ركاز → Run workflow**، واختر فرع **main** وأدخل رقم عملية الفحص المختارة. لا يُستخدم آخر main تلقائيًا. فحص PR مفيد للمراجعة ولكنه لا يكفي للنشر. عند وجود مخاطر SQL لا يبدأ النشر دون مراجعة SQL وإدخال معرّف الاعتماد المعروض في التقرير نفسه؛ هذا إجراء مراجعة بشرية، وليس محلل SQL يضمن سلامة كل تغيير.
4. افتح العملية الجديدة، راجع SHA وخطة الترحيلات، ثم **Review deployments → production-vps → Approve and deploy**. البيئة تتطلب حساب المالك المعتمد ولا تسمح بتجاوز الحماية إداريًا. لأن الحساب له مدير واحد، يسمح بطلب العملية واعتمادها من الشخص نفسه؛ لا توجد مراجعة ثنائية مستقلة.
5. يتصل GitHub بمشغّل مقيد على السيرفر. يعيد التحقق من الإصدار والهدف وسجل الترحيلات وانحراف السحابة والإنتاج، ويختبر البنية والبناء دون مزودين حقيقيين. قبل ترحيل جديد يأخذ dump محميًا ويستعيده في قاعدة مؤقتة معزولة، ثم يطبق الملفات الجديدة فقط، ويبدّل حاوية التطبيق الحالية، ويفحص صحتها. لا يتغير اتصال Lovable أو إعداد تكاملاتها.
6. نجاح المهمة وملف `deployment-result` يوضحان الإصدار والترحيلات المنفذة والفحوص. السجل المفصل والنسخة الاحتياطية يبقيان على السيرفر بصلاحيات root؛ لا يدخلان GitHub artifacts. لا تنشر الرموز أو محتوى ملفات البيئة في التعليقات.

زر النشر لا يظهر بهذه الخطوات حتى اعتماد ودمج ملف workflow في الفرع الافتراضي. في مرحلة التجهيز الحالية `RIKAZ_RELEASE_AUTOMATION_READY=false`، ولا يوجد مفتاح نشر في GitHub؛ هذه بوابات مقصودة تمنع أي نشر عرضي. إعداد البيئة والمراجع متاح فعليًا لهذا المستودع العام، وليس افتراضًا عن خطة مدفوعة.

## فصل البيئتين وتاريخ القاعدة

- السحابة للاختبار فقط، و`https://api.kalmalki.com` لإنتاج VPS. لا تُنسخ بيانات المستخدمين أو التجارب. اختبارات replay تبدأ من schema لنسخة Supabase فارغة مع أدوار المصنع بلا كلمات مرور أو بيانات تطبيق؛ الشبكة `none` والمنافذ الخارجية معدومة وcron متوقف.
- ثبتنا 466 ملفًا مشتركًا وبصمات سجل كل بيئة الفعلية بصورة مستقلة. VPS يحتوي أيضًا على ترحيلة تقليص صلاحيات عملاء الجدول `20261112191931`، المعتمدة سابقًا؛ لا تُرسل إلى السحابة ولا يعاد تطبيقها. اختلاف ترتيب تجزئة statements التاريخي لا يبرر repair أو تعديل سجل مطبّق.
- توجد خمسة ملفات تاريخية استُخدمت لها تسوية معتمدة عند بناء VPS أول مرة. أُرشفت مدخلات ذلك البناء وبصماتها تحت `baseline/historical-replay` لإعادة بناء QA فقط. لم تُعدل ملفات `supabase/migrations` الأصلية أو السجل الحي، ولا تعاد التسوية على قاعدة قائمة.
- يمنع الفاحص حذف/تعديل ملف قديم أو إعادة استخدام رقم، ويتحقق من كل تاريخ مطبق وبصمته. يمنع انحراف البنية والصلاحيات عن replay المتوقع، بما فيه الدوال والسياسات والعلاقات وRLS ومالكو الكائنات والمنح. نشر الإنتاج يفحص السحابة للقراءة ببيانات اعتماد مستقلة. تغير السحابة خارج Git أو وجود ترحيل مجهول يوقف العملية ويحتاج ترحيلة تصحيح معلنة؛ لا تُعالجه الأداة تلقائيًا.
- الفحص يرصد بنية القاعدة والصلاحيات المشمولة في catalog؛ ليس فحصًا لكل بيانات الإعدادات أو Storage bytes أو إعدادات لوحة Supabase أو أسرار المزودين. تغييرات البيانات والإجراءات تحتاج مراجعة خاصة واختبارًا مقصودًا. يُحظر تغيير حدود الطوابير `instance/not_before` داخل الترحيلات.

## التوافق والرجوع

الترتيب الآلي: **توسيع قاعدة متوافق مع التطبيق القديم → تطبيق جديد**. التغييرات الهدامة أو أنواع الأعمدة أو الدوال/DO أو DML أو الصلاحيات تُعلّم للمراجعة. لتغيير يكسر التطبيق القديم استخدم مراحل expand/migrate/contract في إصدارات مستقلة؛ لا يكفي إدخال معرّف اعتماد لإثبات التوافق. تشغيل أتمتة ذلك الإصدار يتوقف حتى تتحدد خطة ملائمة.

المعاملة تشمل ملف SQL الواحد وسجل تطبيقه معًا. عند فشل ملف يتراجع ذلك الملف، وتبقى الملفات السابقة الناجحة مسجلة؛ تتوقف الملفات التالية والتطبيق. قفل على مستوى المشغّل وقفل PostgreSQL يحولان دون تشغيل مزدوج. طلب مكرر يقرأ السجل ولا يعيد تطبيق الملف.

إذا تبدلت الحاوية وفشل فحصها، يعود مشغّل التطبيق للصورة السابقة تلقائيًا فقط لخطة لم تعلّم مخاطر توافق. المخاطر قد تمنع الرجوع؛ حينها تتوقف العملية لتصحيح أمامي ومراجعة. لا يوجد database down/reset أو عكس ترحيلات أو استعادة dump قديم فوق بيانات أحدث. لا تعِد الترحيل يدويًا؛ راجع `failed_phase` و`migrations_applied` ثم صحح السبب وأعد فحص إصدار محدد.

تُوقف مؤقتًا نبضة عامل الرسائل حول تبديل الحاوية وتنتظر انتهاء عمليته، ثم يعاد تشغيله بعد صحة التطبيق. لا تتغير allowlist أو مفاتيح المزودين أو نافذة الرسائل الجديدة؛ لا تُعاد الطوابير التاريخية أو المجهولة. عند فشل خطير قد يبقى العامل متوقفًا للحماية ويحتاج مراجعة السجل، ولا يُفعّل عبر التخمين.

الـdump يشمل قاعدة البيانات ولا يشمل محتوى ملفات Storage على القرص؛ الترحيلات التي تمس التخزين أو حذف الملفات تحتاج نسخة ملفات وخطة خاصة. الاختبار المعزول لصلاحية الاستعادة لا يعني تنفيذ استعادة على الإنتاج.

## الأمن والتهيئة المتبقية

- أسرار التطبيق القائمة لا تدخل GitHub. البناء يستعمل قيم Supabase العامة فقط. رمز قراءة السحابة root-only مستقل، مقيد بالمشروع وبصلاحيات القراءة حسب اعتماد المالك؛ تم التحقق من endpoint القراءة، ولا ندّعي فحص جميع الصلاحيات الممنوحة للرمز من الخدمة.
- `install.py` يجهّز نسخة موثوقة ثابتة تحت `/opt/rikaz-release` وملف إعداد root-only مع `enabled=false`. لا يعدل التطبيق أو MCP أو ينشئ SSH user أو يفعّل نشرًا. نسخة المشغّل الموثوقة لا تُنفذ شيفرة النشر من commit المرشح.
- قبل تمكين النشر يلزم اعتماد اقتراح [MCP](mcp-review/README.ar.md)، وتطبيقه واختباره بصورة مستقلة، ثم إعداد حساب SSH مخصص مع forced command لهذا المشغّل وحده، دون shell أو forwarding، ومفتاح مخصص داخل سر بيئة GitHub، وknown_hosts ببصمة ED25519 المتحققة. لا يستخدم مفتاح root الشخصي في GitHub. تبقى بوابات الاستعداد مغلقة حتى اختبار هذا المسار.
- الحالي MCP يدعم ست أدوات بينها كتابة SQL وترحيلات. المقترح يحصره في أربع أدوات فحص ويصلح قراءة أسماء/أرقام السجل دون نصوص SQL؛ لم يُطبق. لا يُفصل الاتصال أو يُبدل سره. التغيير المنفصل محجوز كاستثناء VPS اختياري مسجل مرة واحدة، ولا تُنشئه ترحيلات التطبيق تلقائيًا.
- changes في Dockerfile/Compose أو baseline أو المشغّل الموثوق تحتاج مراجعة تشغيل مستقلة؛ يمتنع هذا المسار عن استبدالها تلقائيًا. لا PostgreSQL عام ولا MCP داخلي عام ولا صلاحيات نظام عبر MCP.

## خطة الاختبار

تحقق workflow عبر actionlint، ثم اختبارات قرار الاعتماد وتجميد التاريخ والفشل/الرجوع، واختبارات SQL حقيقية في قاعدة معزولة للتزامن والتكرار وذرية السجل وحدود الرسائل والنسخ/الاستعادة. اختبر اقتراح MCP في قاعدة معزولة وبوابة HTTP مع upstream/DB stubs دون لمس MCP الحي. أعد بناء سجل السحابة وسجل VPS المختلف، وقارنهما بالقراءة بالحالة الفعلية. ابنِ Node VPS وCloudflare Lovable وشغّل وحدات التطبيق وTypeScript واختبار runtime معزول. لا اختبار نشر حي أو مزود رسائل أو دور موظف فعلي ضمن هذه المرحلة.
